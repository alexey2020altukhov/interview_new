### WebSocket
WebSocket — это протокол, который позволяет установить постоянное двустороннее соединение между клиентом и сервером.

В обычном HTTP клиент отправляет запрос → сервер отвечает. В WebSocket после установки соединения и клиент, и сервер могут отправлять сообщения друг другу в любой момент.

WebSocket начинается с HTTP handshake, после которого устанавливается постоянное двустороннее соединение. В отличие от обычного HTTP, где клиент инициирует каждый запрос, через WebSocket сервер также может самостоятельно отправлять данные клиенту в любой момент. Поэтому WebSocket используют для чатов, real-time уведомлений, онлайн-игр и других сценариев, где нужна двусторонняя передача данных в реальном времени.

## Spring контейнеры
Spring Framework предоставляет два наиболее фундаментальных и важных пакета, это пакеты org.springframework.beans и org.springframework.context. Код в этих пакетах обеспечивает основу для инверсии функций управления / внедрения зависимостей в Spring. Контейнеры Spring отвечают за создание объектов bean и внедрение их в классы.

**BeanFactory** - самый простой контейнер, обеспечивающий базовую поддержку DI, основан на интерфейсе org.springframework.beans.factory.BeanFactory. Наиболее распространенным классом реализации является XmlBeanFactory.

**ApplicationContext** - обертка поверх BeanFactory, предоставляющая некоторые дополнительные возможности, например AOP, транзакции, безопасность, i18n, и т.п. ApplicationContext - это усовершенствованный контейнер, который расширяет функциональность BeanFactory в более ориентированном на фреймворк стиле. Чаще всего используются следующие реализации: ClassPathXmlApplicationContext, FileSystemXmlApplicationContext, WebXmlApplicationContext, AnnotationConfigWebApplicationContext и т.д.

## BeanFactoryPostProcessor и BeanPostProcessor

**BeanFactoryPostProcessor** позволяет настраивать определения bean-компонентов, а также работать с их конфигурационными метаданными ещё до фактического создания этих bean-компонентов. BeanFactoryPostProcessor создается и запускается перед BeanPostProcessor.

<details>
  <summary>Показать код</summary>
	
```
public interface BeanFactoryPostProcessor {
	public void postProcessBeanFactory(ConfigurableListableBeanFactory beanFactory);
}
```
</details>

**BeanPostProcessor** - это интерфейс, который позволяет вмешиваться в процесс создания и настройки бинов. 
BeanPostProcessor предоставляет два метода, которые можно реализовать:
- postProcessBeforeInitialization: вызывается перед инициализацией бина, используется для изменения или настройки свойств бина перед его инициализацией.
- postProcessAfterInitialization: вызывается после инициализацией бина, используется для изменения или настройки свойств бина после его инициализации.

<details>
  <summary>Показать код</summary>

```
public class MyBeanPostProcessor implements BeanPostProcessor {

	@Override
	public Object postProcessBeforeInitialization(Object bean, String beanName) throws BeansException {
		// Ваш код для изменения или настройки свойств бина перед его инициализацией
		return bean;
	}

	@Override
	public Object postProcessAfterInitialization(Object bean, String beanName) throws BeansException {
		// Ваш код для изменения или настройки свойств бина после его инициализации
		return bean;
	}
}
```
</details>

## @PostConstruct и @PreDestroy
**@PostConstruct** и **@PreDestroy** - аннотации, которые используются для выполнения действий до и после завершения жизненного цикла бина.

**@PostConstruct** используется для аннотирования метода, который необходимо выполнить после создания бина, но до его использования. 

**@PreDestroy** используется для аннотирования метода, который необходимо выполнить перед уничтожением бина.

## HTTP, HTTPS
### Дайте определение HTTP
HTTP (HyperText Transfer Protocol) — это протокол передачи данных между клиентом и сервером.

Из чего состоит HTTP-запрос:
- Метод
- URL
- headers
- Body

### Что такое HTTPS?
HTTPS — это HTTP поверх защищённого соединения TLS.

### Что такое TLS?
TLS шифрует данные между клиентом и сервером.

SSL (Secure Sockets Layer) — старый протокол.
TLS (Transport Layer Security) — его современная замена.

TLS решает три задачи:
- Шифрование (Confidentiality). Никто не может прочитать данные.
- Аутентификация сервера. Клиент проверяет действительно ли он подключился к нужному серверу, а не к поддельному серверу? Для этого используются сертификаты.
- Целостность данных. Нельзя незаметно изменить сообщение.\

### Что такое сертификат?
Сертификат подтверждает: этот публичный ключ принадлежит этому домену

В сертификате есть:
- домен
- публичный ключ
- срок действия
- удостоверяющий центр (CA)
- цифровая подпись

## REST
### Дайте определение REST
REST - сокращение от английского Representational State Transfer - передача состояния представления. Это архитектурный стиль взаимодействия компонентов распределенной системы в компьютерной сети.  

Чтобы система считалась RESTful, она должна “вписываться” в шесть REST ограничений: 
- Приведение архитектуры к модели клиент-сервер. Должно быть четкое разграничение между клиентом и сервером.
- Отсутствие сохранения состояния. Все клиент-серверные операции должны быть без сохранения состояния. Любое необходимое управление состоянием должно осуществляться на клиенте, а не на сервере.
- Кэширование. Все ресурсы должны разрешать кэширование, если явно не указано, что оно невозможно.
- Единообразие интерфейса. Ресурсы должны быть однозначно идентифицированы посредством одного URL-адреса и только с помощью базовых методов сетевого протокола (DELETE, PUT, GET, HTTP).
- Многоуровневая система. REST API допускает архитектуру, которая состоит из нескольких уровней серверов.
- Код по требованию. В большинстве случаев сервер отправляет обратно статические представления ресурсов в формате XML или JSON. Однако при необходимости серверы могут отправлять исполняемый код непосредственно клиенту.

Преимущества, которые дает REST:
- производительность (за счёт использования кэша);
- масштабируемость;
- прозрачность системы взаимодействия;
- простота интерфейсов;
- портативность компонентов;
- лёгкость внесения изменений;
- способность эволюционировать, приспосабливаясь к новым требованиям.

<a name="async-sync-communication"/> 

## Асинхронное/синхронное общение
### В чём разница асинхронного и синхронного общения?
Чтобы обеспечить взаимодействие между микросервисами, используют два распространенных способа: синхронный и асинхронный. В первом случае вызывающая сторона ожидает ответа перед отправкой сообщения, работая как протокол REST (Representational state transfer) поверх HTTP. Во втором — сообщения отправляются, не ожидая ответа. Такой вариант подходит для распределенных систем и обычно нуждается в брокере для управления сообщениями.



<a name="solid"/> 

## Принципы SOLID
### Дайте определение SOLID
1. Single Responsibility Principle - принцип единственной ответственности.
Каждый класс должен отвечать только за одну задачу (должна быть лишь одна причина для его изменения). Если же существуют методы, которые не соответствуют цели сущестствования класса, их необходимо вынести за рамки этого класса.

2. Open Closed Principle (Принцип открытости/закрытости).
Классы должны быть открыты для расширений, но закрыты для модификаций. Когда вы меняете текущее поведение класса, эти изменения сказываются на всех системах, работающих с данным классом. Если хотите, чтобы класс выполнял больше операций, то идеальный вариант – не заменять старые на новые, а добавлять новые к уже существующим.

3. Liskov’s Substitution Principle (Принцип подстановки Барбары Лисков).
Подклассы должны дополнять, а не замещать поведение базового класса. Если объект базового класса заменить объектом его производного класса, то программа должна продолжить работать корректно. Необходимо, чтобы класс-потомок был способен обрабатывать те же запросы, что и родитель, и выдавать тот же результат.

4. Interface Segregation Principle (Принцип разделения интерфейса).
Лучше, когда есть множество специализированных интерфейсов, чем один общий. Не следует ставить клиент в зависимость от методов, которые он не использует. Когда классу приходится производить действия, не несущие никакой реальной пользы, это выливается в пустую трату ресурса, а в случае, если класс выполнять эти действия не способен, ведёт к возникновению багов.

5. Dependency Inversion Principle (Принцип инверсии зависимостей).
Модули верхнего уровня не должны зависеть от модулей нижнего уровня. И те, и другие должны зависеть от абстракций. Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций. Этот принцип служит для того, чтобы устранить зависимость классов верхнего уровня от классов нижнего уровня за счёт введения интерфейсов.

## Kafka
### Что такое Kafka? 
Kafka — гибрид распределённой базы данных и брокера сообщений. 
### Кто такой Publisher (Producer) и Subscriber (Consumer)? 
Producer — компонент, который публикует сообщения в Kafka. 

Consumer — компонент, который читает сообщения из Kafka. 
### Что такое topic? 
Topic — логическая категория/журнал, в который producer отправляет сообщения, а consumer читает их. 

Топики разделяются на партиции, что позволяет распределить данные по брокерам. Каждая партиция реплицируется на несколько брокеров.
### Что такое партиции и зачем они нужны?
Partition — отдельная упорядоченная часть topic. 

Партиции используются для параллельной обработки и масштабирования. Topic разбивается на несколько партиций, и consumer'ы одной группы могут одновременно читать разные партиции. Это позволяет масштабировать обработку. При этом порядок сообщений гарантируется только внутри одной партиции. Поэтому если для одного объекта важен порядок, обычно используют одинаковый key.

Количество партиций фактически задаёт максимальный уровень параллелизма внутри consumer group.

Partitions могут находиться на разных брокерах.

Сообщения распределяются по партициям по ключу партицирования. От каждого сообщения считается hash-функция и высчитывается остаток от деления на число партиций

### Что такое broker?
Broker — сервер Kafka, который хранит partitions и обрабатывает запросы producer'ов и consumer'ов.

Брокеры используются для отказоустойчивости и содержат в себе копии сообщений. Обычно брокера 3.

### Что такое Consumer Group?
Consumer Group — группа потребителей, которые совместно обрабатывают сообщения из топика, каждая партиция читается только одним потребителем из группы.
Потребители делят партиции между собой — растёт пропускная способность. При падении потребителя его партиции подхватывают другие из группы.
Если потребителей больше, чем партиций, то лишние потребители простаивают — они не получают сообщения.

Параллелизм ограничен числом партиций: больше потребителей ≠ больше параллельной обработки.
При сбое работающие потребители подхватят нагрузку, так что «запасные» нужны как резерв для отказоустойчивости.

### Для чего нужна ребалансировка?
Ребалансировка — механизм, при котором Kafka перераспределяет партиции между consumer'ами группы.

Когда происходит rebalance Consumer Group:
- Подключился новый consumer к группе.
- Consumer вышел из группы.
- Consumer упал или перестал отправлять heartbeat.
- Превышен session.timeout.ms — Kafka считает consumer недоступным.
- Превышен max.poll.interval.ms — consumer слишком долго не вызывает poll().
- В topic добавились новые партиции.
- Изменился состав consumer'ов группы по любой другой причине, требующей нового распределения партиций.

### Что такое offset?
Offset - номер первого непрочитанного сообщения внутри партиции.

Подписчики, которые читают записи сообща (параллельно), находятся в одной consumer-группе имеют общие offset'ы.

### Что такое реплика?
Реплика — это копия партиции на другом брокере. Она служит для обеспечения отказоустойчивости и увеличения пропускной способности.

### Как удаляются сообщения из топиков?
Удаляются сообщения согласно 2м стратегиям: по времени (default- неделя) или по размеру очереди.

### Как происходит чтение сообщений?
Consumer делает poll() и получает пачку сообщений. После изучения новой пачки фиксируется новый offset. Настройка max.poll.records определяет максимальное количество сообщений, которое consumer получит за один вызов poll().

Время чтения одной пачки сообщений настраивается через max.pool.intervals.ms. Если consumer не успевает прочитать сообщения за отведенное время, его отстраняют, заменяя следующим, группу перебалансируют.

### Для чего применяют Kafka?
Кафку применяют для:
- Асинхронное взаимодействие. Нам не важен ответ; Последующее действие не зависит от результата асинхронной операции
- Амортизация нагрузки. Отправителю не нужно ждать, когда принимающая сторона обработает всю инфу.
- Потоковая обработка данных. Возможность обрабатывать большое количество сообщений в секунду.
- Репликация данных. Мастер-система пушит в кафку каждое изменение данных, Системы считывают изменения и актуализируют собственные копии мастер-данных.
- Event-driven architecture.

### Какие семантики доставки Kafka существуют?
- At most once — сообщения будут обработаны один раз или не будут обработаны вообще (потеряны).
- At least once — сообщения будут обработаны хотя бы один раз (возможны дубли).
- Exactly once — каждое сообщение будет обрабатано один и только один раз.

При использовании разных семантик доставки производительность системы может быть изменена. Более сильная гарантия может снизить производительность, а более слабая гарантия повысит производительность.

### Что такое идемпотентность?
Идемпотентность — свойство объекта или операции при повторном применении операции к объекту давать тот же результат, что и при первом.

Настройка для producer ниже гарантирует, что одно и то же сообщение будет записано в топик ровно один раз, даже если произошли повторные попытки отправки (например, из-за сетевых сбоев).

### Отличия Kafka от RabbitMQ?
1. Концепция работы с данными 
- Kafka. Реализует концепцию распределённого журнала событий (commit log). Сообщения не удаляются после чтения — они сохраняются на диске в течение заданного срока (retention), и потребители могут перечитывать их в любой момент, отслеживая позицию через смещение (offset). Это делает Kafka идеальной для потоковой аналитики, сбора логов, передачи событий между сервисами в реальном времени. 
- RabbitMQ. Работает как классическая очередь: сообщение удаляется из системы после того, как потребитель его обработал и подтвердил получение. Это удобно для фоновых задач (отправка писем, генерация отчётов), где важно строго однократное выполнение.

2. Модель доставки
- Kafka. Работает по pull-модели: потребители сами опрашивают брокер, чтобы забрать новые сообщения. Это даёт больше контроля и позволяет эффективнее использовать ресурсы.
- RabbitMQ. Использует push-модель: брокер сам активно отправляет сообщения потребителям. Это просто, но требует контроля нагрузки, чтобы потребитель успевал обрабатывать данные.
 
3. Маршрутизация
- Kafka не имеет понятия очередей в классическом смысле. Вместо этого используется модель публикация-подписка (pub-sub), где несколько потребителей могут независимо читать одни и те же данные. 
- RabbitMQ славится гибкой маршрутизацией. Компоненты обменники (exchanges) и очереди (queues) позволяют строить сложные правила пересылки с помощью ключей (routing keys) и разных типов обменов (direct, topic, fanout, headers). 

4. Масштабируемость и производительность
- Kafka оптимизирована для очень высоких нагрузок: она легко масштабируется горизонтально за счёт добавления новых брокеров в кластер. Благодаря последовательной записи на диск и параллельной обработке партиций она способна обрабатывать миллионы сообщений в секунду.
- RabbitMQ хорошо справляется с умеренной нагрузкой и задачами распределения работы между воркерами. При росте числа очередей и потребителей масштабирование требует сложной настройки кластера и не даёт такой же линейной производительности, как в Kafka.

## ACID
### Что такое ACID
ACID - это стандарт того, какие гарантии должна давать база данных, чтобы поддерживать транзакции.

1. Атомарность (atomicity) - гарантирует, что каждая транзакция будет выполнена полностью или не будет выполнена совсем. Не допускаются промежуточные состояния.
2. Согласованность (consistency) - в результате работы транзакции данные будут допустимыми. Это вопрос не технологии, а бизнес-логики: например, если количество денег на счете не может быть отрицательным, логика транзакции должна проверять, не выйдет ли в результате отрицательных значений.
3. Изолированность (isolation) - гарантия того, что параллельные транзакции не будут оказывать влияния на результат других транзакций.
4. Долговечность (durability) - изменения, получившиеся в результате транзакции, должны оставаться сохраненными вне зависимости от каких-либо сбоев. Иначе говоря, если пользователь получил сигнал о завершении транзакции, он может быть уверен, что данные сохранены.

### За счёт чего достигается изолированность?
Изолированность достигается за счёт:
1. Версионирование (snapshot) означает, что транзакции будут работать со своей копией данных, не влияя друг на друга, но впоследствии несколько изменённых копий надо будет как-то слить в одну. Строгость версионирования регулирует моменты (когда) и размеры (сколько данных копировать) этих копий.
2. Блокирование (lock) означает, что одна транзакция будет ждать другую, чтобы избежать побочных эффектов, в зависимости от строгости уровней изоляции этих транзакций. Различные виды блокировок обеспечивают более гранулярное блокирование, например, только по строкам, или только на небольшой кусочек транзакции, а не на всю.

### Какие уровни изолированности существуют?
Уровни изолированности БД:
- READ_UNCOMMITTED (Каждая транзакция видит незафиксированные изменения другой транзакции). Могут происходить грязные чтения, неповторяемые чтения, фантомные чтения и потерянное обновление.
- READ_COMMITTED (Гарантирует, что транзакция видит только подтвержденные изменения других транзакций). Грязные чтения предотвращены, но могут возникать неповторяющиеся чтения, фантомные чтения и потерянное обновление.
- REPEATABLE_READ (Гарантирует, что если транзакция дважды прочитает одни и те же данные, она получит одинаковые результаты) Т.е. мы не видим в исполняющейся транзакции измененные и удаленные записи другой транзакцией. Но все еще видим вставленные записи из другой транзакции). Грязные чтения, неповторяющиеся чтения и потерянное обновление предотвращены, но могут возникать фантомные чтения.
- SERIALIZABLE Транзакции полностью изолированы. Исключено влияние одной транзакции на другую в момент выполнения. Гарантирует, что результат параллельного выполнения транзакций эквивалентен некоторому последовательному их выполнению.

Аномалии:
- Грязное чтение — Dirty Read. Прочитал незакоммиченные данные.
- Неповторяемое чтение — Non-repeatable Read. Прочитал ту же строку, а значение изменилось.
- Фантомное чтение — Phantom Read. Повторил запрос — набор возвращенных строк изменился.
- Потерянное обновление — Lost Update. Две транзакции прочитали одно значение и независимо его изменили. Последняя запись затёрла результат первой.

## Базы данных
### Что такое индекс?
Индекс — это структура данных, которая ускоряет поиск, но требует места и замедляет INSERT/UPDATE/DELETE, потому что индекс нужно поддерживать.
### Виды индексов и их отличия?

### Какие виды индексов существуют в Postgres?
- B-tree (сбалансированное дерево) — обычный индекс общего назначения, используется по умолчанию. Поддерживает все стандартные операции сравнения (>, <, >=, <=, =, <>) и может использоваться с большинством типов данных. B-tree индексы могут быть использованы для сортировки, ограничений уникальности и поиска по диапазону значений. 
- Hash-индексы предназначены для обеспечения быстрого доступа к данным по равенству. Они менее эффективны, чем B-tree индексы, и не поддерживают сортировку или поиск по диапазону значений. Из-за своих ограничений, Hash-индексы редко используются на практике.
- GiST-индексы являются обобщенными и многоцелевыми, предназначены для работы с сложными типами данных, такими как геометрические объекты, текст и массивы. Они позволяют быстро выполнять поиск по пространственным, текстовым и иерархическим данным.
- SP-GiST индексы предназначены для работы с непересекающимися и неравномерно распределенными данными. Они эффективны для поиска в геометрических и IP-адресных данных.
- GIN-индексы применяются для полнотекстового поиска и поиска по массивам, JSON и триграммам. Они обеспечивают высокую производительность при поиске в больших объемах данных.
- BRIN-индексы используются для компактного представления больших объемов данных, особенно когда значения в таблице имеют определенный порядок. Они эффективны для хранения и обработки временных рядов и географических данных.
- Bloom. Фильтр Блума для быстрого отсечения неподходящих строк при проверке множества столбцов на равенство.

### Когда хорошо использовать индексы и когда нет?
Когда индекс хорошо использовать:
1. Частые SELECT по условию WHERE
```
SELECT *
FROM users
WHERE email = 'test@mail.com';

CREATE INDEX idx_users_email
ON users(email);
```
2. Поля с высокой селективностью
Селективность — насколько поле хорошо разделяет данные.

Пример: 1000000 пользователей, 1000000 разных email

Плохо, если 1000000 пользователей и только male и female. Тогда запрос ниже вернёт всего половину таблицы, индекс тут почти не поможет:
```
WHERE gender='male'
```
3. JOIN по колонке
```
SELECT *
FROM orders o
JOIN users u
ON o.user_id = u.id;

CREATE INDEX idx_orders_user_id
ON orders(user_id);
```
4. Частые сортировки
```
SELECT *
FROM orders
ORDER BY created_at DESC;

CREATE INDEX idx_orders_created
ON orders(created_at);
```
5. Foreign Key

Когда индекс плохо использовать:
1. Маленькие таблицы по количеству строк
2. Колонки с низкой кардинальностью. Например, если статус может быть ACTIVE и INACTIVE, но при этом 90% ACTIVE и 10% INACTIVE индекс мало поможет.
3. Слишком много индексов. Тогда INSERT придётся обновить каждые 10 индексов.
4. Индексы, которые не используются. Создали много индексов, но реальные запросы их не используют.
5. Неправильный порядок составного индекса
```
CREATE INDEX idx
ON users(first_name, last_name);

// Хорошо
WHERE first_name='Alex'
AND last_name='Ivanov'

// Хорошо
WHERE first_name='Alex'

//Плохо
WHERE last_name='Ivanov'
```

### Как искать узкие места в запросе к БД? (дописать)
Основной инструмент — EXPLAIN / EXPLAIN ANALYZE.
Если возникает проблема производительности БД, сначала смотрю метрики: CPU, IO, количество соединений, блокировки и долгие запросы. Далее анализирую проблемные SQL через EXPLAIN ANALYZE. Смотрю план выполнения: используются ли индексы, нет ли Seq Scan на больших таблицах, корректна ли статистика, сколько строк реально обрабатывается. Также проверяю N+1, долгие транзакции и блокировки.

### Отличия UNION от INION ALL?
UNION объединяет результаты и удаляет дубликаты.

UNION ALL просто объединяет результаты без удаления дублей.

## Spring
### Что такое Spring?
По сути Spring Framework представляет собой просто контейнер внедрения зависимостей, с несколькими удобными слоями (доступ к базе данных, прокси, аспектно-ориентированное программирование, RPC, веб-инфраструктура MVC). Это все позволяет быстрее и удобнее создавать Java-приложения.

Ключевая особенность приложения, написанного на Spring, состоит в том что большую часть объектов создаем не мы, а Spring. Мы лишь конфигурируем классы (с помощью аннотаций либо в конфигурационном XML), чтобы «объяснить» фреймворку Spring, какие именно объекты он должен создать за нас, и полями каких объектов их сделать. Это и называется инверсией управления или IoC (Inversion of Control). Объекты, которые создаются контейнером и находятся под его управлением, называются бинами. Внедрение зависимости (Dependency Injection) — это и есть инициализация полей бинов другими бинами (зависимостями).

### Области видимости бинов
Области видимости (scope) бинов:
- Singleton (по умолчанию). Бин с данным именем создаётся 1 раз в Spring Application Context и каждый раз при вызове getBean() вызывается тот самый бин. Используется, когда у бина нет изменяемых состояний (stateless)
- Prototype. При вызове getBean() каждый раз будет создаваться новый бин в Spring Application Context. Используется, когда у бина есть изменяемые состояния (statefull)
- Request. Создаётся один экземпляр бина на каждый HTTP запрос. Касается исключительно ApplicationContext.
- Session. Создаётся один экземпляр бина на каждую HTTP сессию. Касается исключительно ApplicationContext.
- Global-session. Создаётся один экземпляр бина на каждую глобальную HTTP сессию. Используется только с портлетами. Касается исключительно ApplicationContext.

### В чём отличие Spring от Spring Boot?
Spring — это основной фреймворк/экосистема.

Spring Boot — это надстройка над Spring, которая максимально упрощает создание и запуск приложения за счёт автоконфигурации, starter-зависимостей и встроенного сервера.

### Какие способы внедрения бинов существуют?
**Способы внедрения бинов:**
- Через конструктор. Преимущество: отсутствие рефлексии, внедрение зависимостей будет работать даже при использовании другого контейнера (не Spring).

Преимуществом является то, что IDEA сразу подсвечивает нам какой бин внедрён (если бин не внедрён, IDEA об этом скажет).

### Почему constructor injection лучше?
Позволяет сделать зависимости обязательными, использовать final-поля, упрощает тестирование и делает код менее связанным.

## JPA, hibernate, ORM
### Что такое JPA?
JPA (Java Persistence API) — это спецификация. То есть набор правил и интерфейсов как Java-объекты должны сохраняться в реляционной БД.

### Что такое Hibernate?
Hibernate — это реализация JPA.

То есть конкретный фреймворк, который выполняет работу:
- Преобразует Java-объекты в SQL;
- Отправляет запросы в БД;
- Управляет состоянием объектов;
- Кеширует данные.

### Что такое ORM?
ORM (Object Relational Mapping, объектно-реляционное отображение) — это технология, которая позволяет работать с базами данных так, как если бы это были объекты из языков программирования. 

### Что такое Persistence Context?
Persistence Context — это область памяти Hibernate, где он хранит управляемые Entity и отслеживает их изменения.

### Какой жизненный цикл Entity?
Жизненный цикл Entity:
- Transient (новый объект)
- Persistent (объект под управлением Hibernate)
- Detached (объект был управляемым, но связь потеряна)
- Removed (объект удаляется)

### Что такое EntityManager?
Это основной объект JPA. Через него Hibernate управляет Entity.
Основные методы:
- find() - получить объект
- persist() - добавить новый объект
- merge() - вернуть detached объект
- remove() - удалить объект

### Для чего нужно кэширование Hibernate и какие его уровни есть?
В Hibernate есть два основных уровня кеша: первый уровень (L1) — Persistence Context, который работает всегда внутри EntityManager, и второй уровень (L2) — общий кеш Hibernate, который работает между сессиями/транзакциями и включается отдельно.

## Связи между Entity и Lazy / Eager Loading
### Что такое FetchType: Lazy и Eager
Lazy Loading (ленивая загрузка) - не загружай связанные данные сразу. Загрузи только когда они понадобятся.

Плюсы Lazy:
- быстрее
- меньше данных
- экономия памяти
Минус: можно получить LazyInitializationException

Eager Loading - загрузи связанные данные сразу

Проблема Eager: можно случайно загрузить слишком много данных.

### Что использовать в реальном проекте Lazy или Eager?
Обычно:
- @ManyToOne → часто оставляют EAGER по умолчанию, но часто меняют на LAZY;
- @OneToMany → почти всегда LAZY.

Хорошая практика: загружать только то, что нужно конкретному сценарию.

### Если на полях сущности, которая является частью транзакции, висит Lazy и мы передаём эти поля в другую сущность или транзакцию, что будет?
Будет ошибка LazyInitializationException

## Проблема N+1
### Что за проблема N+1 и как её решить?
Это ситуация, когда сначала выполняется один запрос для получения списка сущностей, а затем дополнительные запросы для каждой связанной сущности.

Как решить N+1?
- Fetch Join
- EntityGraph
- DTO projection
- правильная настройка загрузки данных

### Cascade в JPA
```
@OneToMany(
    cascade = CascadeType.PERSIST
)
private List<OrderItem> items;
```

В JPA есть:
- CascadeType.PERSIST
- CascadeType.MERGE
- CascadeType.REMOVE
- CascadeType.REFRESH
- CascadeType.DETACH
- CascadeType.ALL

## Базовые паттерны проектирования
Паттерны проектирования — это устоявшиеся удачные решения самых распространнёх проблем, возникающих при проектировании и разработке программ или их частей.  

**1. Порождающие**

## Архитектурные паттерны
### Для чего применяется паттерн API Gateway?
Это единая точка входа в систему. Он скрывает внутреннюю структуру микросервисов, выполняет маршрутизацию, аутентификацию, rate limiting, логирование.

### Что делает BFF (Backend for Frontend)?
BFF (Backend for Frontend) — это отдельный backend-слой, который создаётся под конкретный клиентский интерфейс (например, Web, Mobile, Desktop) и адаптирует данные микросервисов под его потребности.

Что делает BFF?
- Агрегация данных. Делает несколько запросов к разным сервисам, собирает всё в один ответ, удобный для конкретного экрана.
- Адаптация под клиента. Для мобильного приложения отдаёт минимум полей и компактный формат, для веба — более полные данные; для ТВ — крупные картинки и упрощённую структуру.
- Трансформация и фильтрация. Переименовывает поля, меняет структуру JSON, убирает лишние поля, конвертирует форматы (даты, валюты, единицы измерения).
- Упрощение фронтенда. Фронтенд не должен собирать данные из нескольких эндпоинтов, делать параллельные запросы и склеивать ответы — это берёт на себя BFF.
- Изоляция изменений. Изменения в API внутренних сервисов не должны ломать клиентов: BFF скрывает внутреннюю сложность и стабилизирует контракт с фронтендом.
- Авторизация и безопасность. BFF может: проверить JWT, получить user context, добавить необходимые заголовки, скрыть внутренние API.

### Чем отличается Api Gateway и BFF?
API Gateway — это единая точка входа в микросервисную систему. Он отвечает в основном за инфраструктурные задачи: маршрутизацию запросов, авторизацию, аутентификацию, ограничение количества запросов, логирование и мониторинг. Он не должен содержать бизнес-логику.

BFF (Backend for Frontend) — это отдельный backend, который создаётся под конкретный клиент: например, отдельно для мобильного приложения и отдельно для веб-приложения. Его задача — адаптировать API микросервисов под потребности конкретного фронтенда: объединять данные из нескольких сервисов, преобразовывать ответы и уменьшать количество запросов от клиента.

### CQRS - для чего применяется?
CQRS — это паттерн, при котором разделяют операции изменения данных (Command) и операции чтения данных (Query).

Главная идея - запись и чтение могут иметь разные модели данных и оптимизироваться независимо друг от друга.

### Зачем нужен паттерн Transactional Outbox
Transactional Outbox описывает общий подход для хранения завершенных транзакций. При выполнении транзакции (например, когда идёт сохранение какой-либо сущности) в рамках этой же транзакции также сохраняется информация об этом действии в отдельную таблицу (например, outbox). Потом сторонний scheduler через определенные интервалы времени заглядывает в эту таблицу. Если запись там есть, то выполняет следующую транзакцию (или отправляет данные в брокер сообщений).

Если бизнес-объект и соответствующие сообщения сохраняются в рамках одной транзакции базы данных, это гарантирует, что данные не будут потеряны. Либо будет зафиксировано все, либо при возникновении ошибки произойдет полный откат.

Если описывать кратко, то это паттерн, который решает проблему: как гарантировать, что после изменения данных в БД событие точно уйдёт в брокер сообщений (например, Kafka).

### Для чего применяется паттерн Database per Service?
Каждый микросервис владеет своей базой данных и полностью отвечает за свои данные. Другие сервисы не должны напрямую обращаться к его БД.

### Зачем применяют Circuit Breaker?
Circuit Breaker предотвращает попытки приложения выполнить операцию, которая скорее всего завершится неудачно, что позволяет продолжить работу дальше не тратя важные ресурсы, пока известно, что проблема не устранена. Приложение должно быстро принять сбой операции и обработать его.

Он также позволяет приложению определять, была ли устранена неисправность. Если проблема устранена, приложение может попытаться вызвать операцию снова.

Например, один микросервис отправляет запрос к другому микросервису. Паттерн позволяет не ждать ответа, а сразу вернуть ошибку в случае его недоступности.

### Для чего предназначен паттерн Retry?
Retry обеспечивает повторение операции при возникновении временного сбоя – вместо немедленного отказа. Помогает справиться с кратковременными проблемами в сети или сервисах.

### В чём смысла паттерна Async Messaging 
Async Messaging предполагает использование очередей сообщений для асинхронной коммуникации. Это может улучшить отзывчивость системы и ее масштабируемость, так как сервисы не блокируются в ожидании ответа друг от друга.

### Для чего применяют паттерн Saga?

**Saga** - предоставляет механизм, который позволяет обеспечить согласованность данных в микросервисной архитектуре без применения распределенных транзакций.

Сага представляет собой набор локальных транзакций. Каждая локальная транзакция обновляет базу данных и публикует сообщение или событие, инициируя следующую локальную транзакцию в саге. Если транзакция завершилась неудачей, например, из-за нарушения бизнес правил, тогда сага запускает компенсирующие транзакции, которые откатывают изменения, сделанные предшествующими локальными транзакциями.

Типы транзакций в саге:

- Компенсирующая — отменяет изменение, сделанное локальной транзакцией.
- Компенсируемая — это транзакция, которую необходимо компенсировать (отменить) в случае, если последующие транзакции завершаются неудачей.
- Поворотная — транзакция, опеределяющая успешность всей саги. Если она выполняется успешно, то сага гарантированно дойдет до конца.
- Повторяемая — идет после поворотной и гарантированно завершается успехом.

Существует два способа координации саг:  
- Хореография (Choreography) — каждая транзакция публикует события, которые запускают транзакции в других сервисах.
- Оркестровка (Orchestration) — оркестратор говорит участникам, какие транзакции должны быть запущены.

## Транзации Spring
### Что такое транзакция?
Транзакцией называется набор связанных операций, все из которых должны быть выполнены корректно без ошибок. Если при выполнении одной из операций возникла ошибка, все остальные должны быть отменены. Прежде всего такой механизм применяется при работе с БД.

### Будет ли при вызове method2 из метода method1 создана новая транзакция?
```
public class MyServiceImpl {

    @Transactional
    public void method1() {
        //do something
        method2();
    }

    @Transactional(propagation=Propagation.REQUIRES_NEW)
    public void method2() {
        //do something
    }
}
```

Для поддержки транзакций через аннотации используется Spring AOP, в момент вызова method1() на самом деле вызывается метод прокси объекта. Создается новая транзакция и далее происходит вызов method1() класса MyServiceImpl. А когда из method1() вызовем method2(), обращения к прокси нет, вызывается уже сразу метод нашего класса и, соответственно, никаких новых транзакций создаваться не будет.

Как сделать, чтобы создавалась новая транзакция в этом случае?
1. Вынести method2 в отдельный Spring Bean
2. Self-inject класса и вызов метода через него (вызвать внутри одного метода другой через бин этого же класса). Прим.: Работает только для бинов со scope singleton, для prototype при старте приложения упадёт ошибка циклического внедрения бина самого в себя
3. Использовать TransactionManager

### Для чего в @Transactional используется Propagation?
Propagation (распространение транзакции) — это правило, которое определяет, что делать с текущей транзакцией, когда один транзакционный метод вызывает другой транзакционный метод.
```
@Transactional(propagation = Propagation.REQUIRED)
```
- REQUIRED (по умолчанию). Использовать существующую транзакцию, если она есть. Если нет — создать новую.
- REQUIRES_NEW. Всегда создать новую транзакцию.
- MANDATORY. Требует существующую транзакцию. Если её нет — ошибка.
- SUPPORTS. Использует транзакцию, если она есть, иначе работает без неё.
- NOT_SUPPORTED. Всегда выполняется без транзакции.
- NEVER. Запрещает выполнение внутри транзакции.
- NESTED. Создаёт вложенную транзакцию через savepoint.

### Как работают транзакции в Spring под капотом?
Spring реализует транзакции через AOP-прокси. При вызове метода с @Transactional прокси перехватывает вызов, через TransactionManager открывает транзакцию и привязывает ресурсы к текущему потоку. Затем выполняется бизнес-метод. После успешного завершения выполняется commit, при исключении — rollback. Поэтому транзакции не работают при self-invocation, так как внутренний вызов не проходит через прокси.

### Какие виды блокировок есть в Spring?
Основные:
1. Оптимистические (Optimistic Lock). Optimistic Lock (оптимистическая блокировка). Мы не блокируем данные, считаем, что конфликты редкие, но проверяем перед сохранением, что данные никто не изменил.
```
@Entity
public class Product {

    @Id
    private Long id;

    private Integer count;


    @Version
    private Long version;
}
```
Если кто-то изменил данные выкидывает OptimisticLockException.
+ нет блокировок в БД
+ высокая производительность
+ хорошо для большого количества чтений
- конфликт обнаруживается только в момент сохранения
- нужно обработать ошибку

2. Пессимистические (Pessimistic Lock). 
Мы заранее блокируем запись, потому что ожидаем конфликт.
```
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Product> findById(Long id);
```
Hibernate выполнит:
```
SELECT *
FROM product
WHERE id=1
FOR UPDATE;

// С for update бд ставит блокировку на строку
```

Виды Pessimistic Lock в JPA:
- PESSIMISTIC_READ - другие транзакции могут читать, но не могут изменять.
- PESSIMISTIC_WRITE - Другие транзакции не могут изменить, взять такую же блокировку.
- PESSIMISTIC_FORCE_INCREMENT. Как WRITE, но ещё увеличивает @Version.

## Redis
### Что такое Redis?
Redis — это in-memory хранилище данных. То есть данные находятся в оперативной памяти, поэтому доступ к ним очень быстрый. Redis обычно используют как быстрый слой между приложением и основной БД. Основные сценарии — кеширование часто читаемых данных, хранение сессий, rate limiting и временные данные. Чаще всего используется паттерн Cache Aside: сначала проверяем Redis, при отсутствии читаем из БД и кладём результат в кеш. При обновлении данных обычно инвалидируем кеш, чтобы избежать рассинхронизации.

Нужен для
- Кеширование данных
- Хранение сессий
- Rate limiting
- Очереди и временные данные

### Как Redis хранит данные?
Redis хранит данные в формате ключ → значение (key-value), но значение может иметь разные структуры данных (String, Hash, List, Set, Sorted Set и т.д.).

### Какие структуры данных есть в Redis?
- String — простая пара ключ-значение для хранения строк, чисел, токенов, кеша, счётчиков.
- Hash — структура вида объект/Map, где один ключ содержит набор полей и значений (например, данные пользователя).
- List — упорядоченный список элементов, используется для простых очередей, истории сообщений.
- Set — множество уникальных элементов без сортировки, используется для хранения уникальных значений, тегов, участников.
- Sorted Set (ZSet) — множество с дополнительным числовым рейтингом (score), используется для рейтингов, топов, очередей с приоритетом.
- Bitmap — битовая структура поверх String, используется для компактного хранения флагов и статистики.
- HyperLogLog — структура для приблизительного подсчёта количества уникальных элементов с минимальным потреблением памяти.
- Stream — структура журнала событий с поддержкой сообщений, идентификаторов и групп потребителей, похожа на упрощённый Kafka.
- Geo — структура для хранения координат и поиска объектов по расстоянию (например, ближайшие магазины или пользователи).
